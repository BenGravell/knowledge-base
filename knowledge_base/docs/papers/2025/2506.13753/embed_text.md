## Introduction

In the motion planning problem we are given a robot $r$, an environment $E$, and two configurations of $r$ in $E$, denoted $s$ and $t$, and are tasked with finding a valid set of motions of $r$ that would take it from configuration $s$ to $t$. A motion is valid (or collision-free) if it does not result in $r$colliding with itself or any object in the environment.

The problem's intractability [r-cmpg-79] lead to the development of randomized sampling based approaches. These sampling based motion planning (\Term{SBMP}\xspace) algorithms reduce the problem to finding an $(s,t)$-curve in the implicit configuration space (c-space) [l-spcsa-83] defined by $r$ and $E$ that does not contain any point representing an invalid configuration. These methods create a geometric graph in c-space, also known as a roadmap, by sampling random points (configurations) and using them to expand the graph. The problem is then reduced further to that of finding a $(s,t)$-path in the graph.

The process of expanding the geometric graph given a sampled point uses a neighborhood finder subroutine to find a set $N$ of candidate points. \Term{RRT}\xspaceand \Term{RRG}\xspaceextend new graph edges from every point in $q\in N$ towards $p$, but stop the extension process if an invalid configuration is found or a predetermined distance has been reached, and add an edge possibly spanning a partial trajectory between $q$ and $p$. The probabilistic roadmap (\Term{PRM}\xspace) algorithm, on the other hand, will not add a partial edge, and will only connect $p$ and $q$ if the entire trajectory is collision-free, allowing users to opt for collision checking the edge in a non-linear fashion. As hinted by the names of the algorithms, \Term{RRT}\xspacewill use a neighborhood finder such that $|N|=1$, creating a tree, while \Term{RRG}\xspaceand \Term{PRM}\xspacerequire larger The neighborhood finder subroutine takes a c-space graph c-space point $c$ as arguments, and returns a discrete set of points $N_G(c) \subseteq G$ according to some heuristic, usually the $k$ nearest neighbors (\ensuremath{k\mathtt{NN}}) according to a chosen distance metric. Existing neighborhood finders focus on returning a subset of the graph's vertices while ignoring its edges, even though these edges are often nothing more than a dense sequence of configurations individually checked for collision in a slow and expensive process.

This gap can be explained by two properties of the geometric space, c-space, in which this computation is performed, 1) it can be of arbitrarily high dimensionality, and 2) it can be a mixture of Euclidean and non-Euclidean dimensions. Standard algorithms and data structures applicable in those conditions are somewhat scarce. For example, the Computational Geometry Algorithms Library (CGAL) [t-curm-24], the most widely used computational geometry library, does not have off-the-shelf $d$-dimensional point-to-segment distance computation or a $d$-dimensional axis-aligned bounding box tree (\Term{AABB}\xspace-tree) for segments when $d>3$, and does not have a standard kernel for a mix of dimension types.

Using a neighborhood finder capable of returning arbitrary points on the tree's swath substitutes the simple Voronoi exploration bias \Term{RRT}\xspace, where tree vertex is extended with probability proportional to the measure of its cell in the Voronoi diagram of the tree's nodes, in a similar bias that extends from either an interior of an edge or from a vertex with probability proportional to the measure of the Voronoi cell of that object in the Voronoi diagram of points and segments induced by the graph. See [fig:voronoi:diff]Fig.\ref*fig:voronoi:difffor an illustration of this difference for a 2D scenario.

In (a) the set of candidates is the vertices only, and in (b) it is the entire swath of the tree. fig:voronoi:diff In this paper we present the edge-\ensuremath{\mathtt{NN}}\xspace neighborhood finder, which can return the point on a $d$-dimensional segment in $\mathbb{R}^{\mathcalb{t}}\times \mathbb{T}^{\mathcalb{r}}$, where $\mathbb{T}^i$ is the $i$-dimensional torus, closest to a query point. The neighborhood finder is based on mixed-$d$-dimensional distance computation primitives that form the basis for an \Term{AABB}\xspace-tree capable of storing a set of segments $S \subseteq \mathbb{R}^{\mathcalb{r}}\times \mathbb{T}^{\mathcalb{t}}$ and answering approximate $\ensuremath{k\mathtt{NN}}$queries for query points.

We formally prove that this neighborhood finder is expected to produce c-space graphs with shorter edges when used to construct a geometric graph, and experimentally show improvement for \Term{RRT}\xspacewhich performs less collision detection (CD) calls when using our method compared with neighborhood finders considering only graph vertices. This improvement can be attributed both to the shorter length of the graphs edges and to a superior exploration bias.

### Related Work

An approximate solution which stores intermediates along edges in a $kD$-tree for the purpose of nearest neighbor queries is also suggested as a simple and effective compromise. In practice, implementations of \Term{RRT}\xspaceusually consider only tree vertices as candidates from which to extend new \Term{RRG}\xspacealgorithm [f-isaom-10] is a variant of \Term{RRT}\xspacethat, instead if extending a single edge at every iteration, extends such edges from all neighbor vertices within a certain distance of the sample, thus creating a roadmap graph instead of a tree.

## The new neighborhood finder

In this section, we describe the edge- \ensuremath{k\mathtt{NN}} neighborhood finder and its building blocks. As a reminder, the configuration space is $\ensuremath{\mathcal{C}_{space}}=\mathbb{R}^{\mathcalb{t}}\times\mathbb{T}^{\mathcalb{r}}$, and the input is a set of line segments $S\subseteq \ensuremath{\mathcal{C}_{space}}$. Our purpose is to build a data structure that stores $S$, and answers $(1+\varepsilon)$-approximate $\ensuremath{k\mathtt{NN}}{}$ point queries for a predetermined $\varepsilon > 0$. That is, given a point $p\in\ensuremath{\mathcal{C}_{space}}$ and an integer $k$, return a set of $k$ segments such that the distance of the $i$th\xspacesegment $s_i$ from $p$, $\dcY{p}{s_i}$, is within a factor of $(1+\varepsilon)$ from $p$'s $i$th\xspacenearest neighbor in $S$.

We first present the basic geometric operations modified to work in $\ensuremath{\mathcal{C}_{space}}$, and then use them to build an \Term{AABB}\xspace-tree \Term{AABB}\xspace= Axis-Aligned Bounding Box. for $\ensuremath{\mathcal{C}_{space}}$ segments that supports approximate $\ensuremath{k\mathtt{NN}}$ queries for points of $\ensuremath{\mathcal{C}_{space}}$. This \Term{AABB}\xspace-tree is the main component of our neighborhood finder, and can return a set of $k$ neighbors of a point $p\in \ensuremath{\mathcal{C}_{space}}$ such that $\ensuremath{\mathcal{C}_{space}}$segments, edges of the c-space graph, may contain a single member of the \Term{AABB}\xspace-tree is a modified $kd$-tree for storing segments, and answering nearest-neighbor and intersection queries. The wrinkle is that we need to support rotational coordinates, and we next describe the basic geometric primitives necessary to implement this efficiently. We describe the \Term{AABB}\xspace-tree in more detail in [sec:neighborhood:finder]Section\ref*sec:neighborhood:finder.

### Edge-\ensuremath{k\mathtt{NN}} neighborhood finder

sec:neighborhood:finder Using the simple operations described above we construct an \Term{AABB}\xspace-tree to store the $d$-dimensional segments and answer approximate $\ensuremath{k\mathtt{NN}}$ queries using a simplified version of the well known algorithm by Arya \textit{et~al.}\xspace[amnsw-oaann-98].

Our tree is built by recursively splitting an \Term{AABB}\xspacecontaining a set of segments into at most three children nodes, starting at the root with an \Term{AABB}\xspacethe full list. When splitting a node we define an axis-parallel hyperplane that splits the segments into three roughly equal groups, two sets that are fully contained in either sides, and one set of all segments that intersect the hyperplane.

The set of segments is cutting the graph's edges as described above, and maintains a mapping between these and their parent graph edge. The $\ensuremath{k\mathtt{NN}}$ query makes sure to only keep at most one childof each edge in the heap containing the nearest neighbors, while still checking children of an edge even if another child is already in the Upon finishing the $\ensuremath{k\mathtt{NN}}$ query with a set of c-space segments and the points on these segments closest to $p$, the data structure uses the mapping to get the corresponding set of edges and returns both the edge IDs and the closest points to the \Term{SBMP}\xspacealgorithm, so that it could test for a connection/extension between them and the sampled point $p$. Note that some of the edges might be degenerated, meaning vertices of the $\ensuremath{\mathcal{C}_{space}}$graph, but otherwise the edge is split in two at the endpoint of the newly added edge.

The tree is parameterized by several quantities: $n_{\mathrm{leaf_thresh}}$is the threshold for the number of segments that will trigger a further split (as opposed to making the node a leaf). $n_{\mathrm{buff}}$is the size of the buffer for edge insertion. When the buffer is full the tree is rebuilt with all of the previous edges and the ones stored in the buffer. $n_{\mathrm{leaf_ratio}}$ is the threshold ratio between the number of segments stored in the child node to that stored in the parent. If a child contains more than $n_{leaf_ratio}$ times the number of segments in its parent it becomes a leaf. This parameter is crucial to deal with edge cases in which a set of segments cannot be even somewhat evenly split by any axis-parallel The tree also supports deletions using a deletion buffer that prevents deleted segments from being considered as neighbors and from being included when the tree is rebuilt.

## cobweb-\Term{RRG}\xspace: Motion planning algorithm

### The cobweb algorithm

The exploration bias of the edge- \ensuremath{\mathtt{NN}}\xspaceneighborhood finder provides us with a simple heuristic for finding narrow passages in c-space using extensions. In the presence of a narrow passage, \Term{RRT}\xspacerequires a vertex of the tree relatively close to the passage, and a sample in the rightdirection that would lead to an extension of an edge into the passage. [fig:cobweb:vertex:extend]Fig.\ref*fig:cobweb:vertex:extend, the vertices of the tree might not be situated in useful locations. Namely, the region from which a sample must be drawn can be of a tiny measure. When using edge-\ensuremath{\mathtt{NN}}\xspace, an edge of the tree shooting across the narrow passage is enough to give rise to a set of bigger measure of beneficial samples, as [fig:cobweb:edge:extend]Fig.\ref*fig:cobweb:edge:extendillustrates.

We propose the Cobweb algorithm (cobweb-\Term{RRG}\xspace), a variant of \Term{RRG}\xspacedesigned to take advantage of the properties of edge-\ensuremath{\mathtt{NN}}\xspace. cobweb-\Term{RRG}\xspacemimics \Term{RRT}\xspacein open regions of c-space, and span webs of edges across regions of contact-space, the boundary between free-space and obstacle-space, the subsets of c-space that form the natural partition to valid and invalid configurations respectively, where the openings of narrow passages may exist. See [fig:cobweb:intuition]Fig.\ref*fig:cobweb:intuition for an illustration of the intuition the idea is to create a net-like structure (i.e., cobweb) that can cover the entry of a (potentially narrow) tunnel. Then, a sample that leads from the net into the tunnel would facilitate finding a solution (hopefully quickly). ## Theoretical analysis

sec:theoretical:analysis The intuition regarding the use edge nearest neighbors is straightforward. Choosing the nearest neighbor from a much larger set of candidates, in this case a large set of intermediate points on the edges, will result in shorter edges, which in turn leads to less CD calls and faster runtimes. See [fig:voronoi:diff]Fig.\ref*fig:voronoi:diff for a 2D illustration. For $n\longrightarrow \infty$, $n$ being the number of sampled configurations, this intuition is true in any motion planning scenario, but for a given $n$we cannot prove a catch-all lemma guaranteeing a reduction of overall edge lengths due to pathological cases, e.g. a c-space consisting of a narrow 2-dimensional annulus. Instead, we prove a lemma that formalizes the aforementioned intuition and captures many reasonable motion planning scenarios. $B$ be the $d$-dimensional box, and let $P\subseteq B$ be a sequence $(p_1,...,p_n)$ of $n$ points chosen uniformly at random from $B$. ## Discussion

Unsurprisingly, the results of the roadmap length experiments conducted in empty environments described in [sec:empty:experiment]Section\ref*sec:empty:experiment corroborate the simple intuition, and, to a certain degree, the theoretic findings proven in [sec:theoretical:analysis]Section\ref*sec:theoretical:analysis. The variance in these experiments was low, meaning that the results shown in [table:empty:experiment]Table\ref*table:empty:experiment truthfully represent the gap between using vertex-\ensuremath{\mathtt{NN}}\xspace and edge-\ensuremath{\mathtt{NN}}\xspace. As expected, as the number of \Term{DOF}\xspaces grows, the effect of using our algorithm diminishes, but when using \Term{PRM}\xspaceand as the number of connections ($k$) increases, the advantage becomes well pronounced. A curious finding not shown in the data, is that even though in every iteration of \Term{RRT}\xspacethe neighbor found with edge-\ensuremath{\mathtt{NN}}\xspace is closer to the sample than that found by vertex-\ensuremath{\mathtt{NN}}\xspace, using the same seed of course and thus the same sample, in many iterations the extension distance achieved using the former neighborhood finder was greater.

The motion planning experiments described in [sec:mp:experiment]Section\ref*sec:mp:experiment contain several interesting results. First, we see that edge-\ensuremath{\mathtt{NN}}\xspace provides superior exploration guidance in the presence of narrow passages, where its advantage is so pronounced that it meaningfully affects the runtime of \Term{RRT}\xspaceregardless of the longer runtime required by its \ensuremath{\mathtt{NN}}\xspacefunction. However, this advantage can be seen in all of the experiments, and expresses itself also in the lower number of iterations required to complete all of the motion planning tasks, and this is - as a reminder, even though the different neighborhood finders compete using the same random seeds. However, the cost of using a more complex neighborhood finder is reflected in worse runtimes for easier motion planning tasks in simple environments, i.e. where the combinatorial complexity of the robot and the set of obstacles is relatively low.
